# План проекта DevOps LLM-агента

## 1. Видение и цели
- Создать автономного помощника, работающего как инженер DevOps в неоднородных инфраструктурах (bare metal, виртуальные машины, контейнеры, кластеры Kubernetes).
- Обеспечить способность агента анализировать состояние инфраструктуры, формировать безопасные команды, выполнять их через SSH/Docker/Kubernetes API и проверять результат с минимальным участием человека.
- Реализовать строгие предохранители, наблюдаемость и рабочие процессы для запроса ручного подтверждения при высоком риске.

## 2. Основные персоны и сценарии
- **Инженер DevOps/SRE:** делегирует рутинное обслуживание, immutable-деплойменты, триаж инцидентов, генерацию отчётов.
- **Платформенные команды:** предоставляют широким командам доступ к платформенным операциям через контролируемый разговорный интерфейс.
- **Дежурные инженеры:** используют агента для ускоренного реагирования на инциденты, сбора логов/метрик и предложений по ремедиации.

## 3. Ключевые функциональные требования
1. Подключение к удалённым системам по SSH (джамп-хосты, бастионы, портфорвардинг) и выполнение команд с настраиваемым повышением привилегий.
2. Взаимодействие с системами оркестрации контейнеров:
   - Docker: операции жизненного цикла, управление образами, получение логов и метрик.
   - Kubernetes: переключение контекстов, инспекция ресурсов, rollout/rollback, применение манифестов, интеграция с Helm/Argo.
3. Понимание инфраструктурного кода (Terraform, Ansible, Helm) и CI/CD-пайплайнов для обоснования изменений.
4. Получение ответов с опорой на внутренние runbook'и, документацию и предыдущие инциденты.
5. Человеческий контроль: dry-run, этапы согласования, политики исполнения, отчёты о выполнении.
6. Многоуровневый интерфейс: веб-чат, CLI-ассистент и API для автоматизации.
7. Ведение аудит-логов входных данных, действий, результатов и решений.

## 4. Нефункциональные требования
- **Безопасность:** zero-trust подход, креденшалы с минимальными правами, секреты через vault, журналирование каждого действия.
- **Надёжность:** самовосстановление сервисов агента, деградация в случае отказа LLM или инструментов, стратегии повторов.
- **Задержки:** время планирования не более 5 секунд для большинства запросов; потоковая выдача для длительных операций.
- **Расширяемость:** модульные адаптеры инструментов, плагинная архитектура для новых сервисов (SDK облаков, мониторинг).
- **Соответствие требованиям:** журналирование в формате, удобном для SOC2, автоматическое удаление PI/PHI, опциональный контроль локализации данных.

## 5. Обзор архитектуры
### 5.1 Слой взаимодействия
- Веб-чат с управлением сессиями, рендерингом Markdown и предпросмотром команд.
- CLI-утилита для продвинутых пользователей с потоковым выводом TTY и локальным контекстом.
- REST/gRPC API для интеграции агента в другие процессы.

### 5.2 Слой рассуждений и оркестрации
- Основная LLM — Google Gemini 1.5 (облачная) и локальные модели через Ollama; маршрутизатор обеспечивает соблюдение SLA по стоимости и задержкам и готов к подключению новых провайдеров.
- Цикл агентного планирования «plan→act→observe», реализованный с помощью графового планировщика и контроллера выполнения.
- Модули памяти:
   - Краткосрочное состояние диалога (на сессию).
   - Долговременная база знаний с векторным хранилищем.
   - Рабочий блокнот задач для многошаговых операций.
- Политиковый движок, ограничивающий допустимые команды, требующий согласования и оценивающий риски.
- Реестр окружений с метаданными (прокси, сетевые сегменты, версии кластеров, требуемые политики) и автоматическое подтягивание конфигураций в планировщик.

### 5.3 Слой инструментов и интеграций
- **SSH-исполнитель:** обёртка над `asyncssh`/`paramiko`, поддержка цепочек джамп-хостов, MFA, sudo, потокового вывода.
- **Адаптер Docker:** использование Docker Engine API/SDK, песочница команд, отслеживание diff, просмотр логов.
- **Адаптер Kubernetes:** client-go или Python SDK `kubernetes`, динамическое переключение контекстов, приём наследуемых ролей, шаблонизация манифестов.
- **Адаптеры IaC:** обёртка Terraform CLI, runner для Ansible, клиенты Helm/ArgoCD.
- **Интеграции наблюдаемости:** Prometheus, Grafana, ELK, Datadog, CloudWatch для получения метрик и логов.
- **Коннекторы уведомлений:** Slack/Teams, PagerDuty для эскалаций.

### 5.4 Слой данных и хранения
- Векторная база (pgvector, Weaviate, Pinecone) для эмбеддингов.
- Хранилище документов (PostgreSQL/S3) для runbook'ов, транскриптов сессий, выводов команд.
- Управление секретами через HashiCorp Vault или облачный KMS.

### 5.5 Слой безопасности и комплаенса
- Классификация команд (низкий/средний/высокий риск) с маршрутами согласования по политикам.
- Песочница для dry-run (контейнеризированный прогон) перед выполнением в проде, когда возможно.
- Конвейер редактирования, удаляющий секреты/PII из логов и промптов.
- Аудит-конвейер, отправляющий структурированные события в SIEM.

## 6. Рекомендуемый технологический стек и языки
- **Основные языки:** Python 3.11 (оркестратор, API, интеграции), TypeScript 5.x (Next.js фронтенд), Go 1.22 (CLI и высоконагруженные адаптеры), Bash (bootstrap/операции), HCL (Terraform), YAML (Helm/k8s).
- **Серверный контур:** FastAPI + Pydantic v2 для HTTP/gRPC API, Celery или Temporal/Prefect для фоновых задач, Redis Streams как шина событий, WebSocket-стриминг на Starlette.
- **Агентный уровень:** LangChain + LangGraph или LlamaIndex для построения графов действий, лёгкий маршрутизатор провайдеров (liteLLM/open source альтернатива) с поддержкой горячего подключения новых API, встроенные guardrails (Guardrails.ai, OpenAI Evals) и memory store на Redis/pgvector.
- **Обработка LLM:** приоритетные провайдеры — Google Gemini 1.5 (официальный SDK) и локальный Ollama API (Llama 3, Mixtral); архитектура через абстрактный интерфейс `LLMProvider` позволяет быстро добавить OpenAI/Anthropic/Azure при необходимости; эмбеддинги — Gemini Embeddings + локальные bge-m3 для конфиденциальных данных.
- **Хранение и данные:** PostgreSQL 15/16 (состояние, аудит), Redis 7 (кэш, rate limiting), MinIO/S3 (артефакты, логи), pgvector/Weaviate для эмбеддингов, Elastic/Loki для логов.
- **Интеграции и инструменты:** AsyncSSH/Paramiko, kubernetes Python client + client-go, python-terraform, docker SDK (Python/Go), Prometheus/Grafana API, Slack Bolt/Teams Graph API, PagerDuty Events API.
- **Фронтенд и DevX:** Next.js 14 (App Router) + Tailwind + Radix UI, Zustand/TanStack Query для состояния; CLI на Go (Cobra) либо Python Typer; Storybook для документирования компонентов.
- **Инфраструктура и CI/CD:** Terraform + Terragrunt для IaaS, Helm + ArgoCD/Flux для GitOps, GitHub Actions (reusable workflows) + BuildKit, Docker Compose и kind/k3d для локальной разработки, Vault/External Secrets Operator для секретов.

## 7. Логика работы агента
1. **Приём запроса:** получение промпта с метаданными сессии и параметрами окружения (кластер, namespace, группа хостов).
2. **Сбор контекста:** подтягивание runbook'ов, предыдущих команд, состояния инфраструктуры (CMDB/API) и правил политики.
3. **Планирование:** агент-планировщик разбивает задачу на шаги, оценивает риск по каждому шагу, запрашивает подтверждения при необходимости.
4. **Вызов инструментов:** исполнитель вызывает соответствующие адаптеры (SSH/k8s и т.д.) со структурированными параметрами и стримит вывод.
5. **Верификация:** постпроверки сравнивают ожидаемое и фактическое состояние (деплоймент, здоровье сервисов).
6. **Резюме:** агент формирует отчёт с действиями, доказательствами и дальнейшими шагами.
7. **Обновление памяти:** сохранение диалогов, результатов, телеметрии для повторного использования и аудита.

### Распределение на подагенты
- **Planner Agent:** понимание запроса, построение графа задач, оценка рисков.
- **Executor Agent:** детерминированная генерация команд, взаимодействие с адаптерами, обработка ретраев.
- **Verifier Agent:** проверяет результаты, запускает смоук-тесты, ищет аномалии (например, ошибки в логах).
- **Knowledge Agent:** поддерживает векторную базу, ищет документы, обновляет знания новыми выводами.

## 8. Архитектура безопасности
- Аутентификация пользователей через OIDC/SAML SSO, отображение идентичностей на политики RBAC.
- Краткоживущие креденшалы (Vault-выданные SSH-сертификаты, токены сервисных аккаунтов AWS/GCP).
- Подтверждение команд посредством подписанных аттестатов; неизменяемые аудит-логи (AWS QLDB или append-only стор).
- Сегментация сети: сервисы агента в приватных подсетях с исходящим трафиком через прокси.
- Цифровая проверка документов для защиты от prompt-injection.
- Rate limiting и обнаружение аномалий подозрительного поведения.

## 9. Развёртывание и эксплуатация
- **Окружения:** дев-сэндбокс (моки адаптеров), стейджинг (ограниченный доступ к реальным кластерам), прод (тенантные сегменты).
- **Пакетирование:** микросервисы (api-gateway, оркестратор, tool-runner'ы, векторное хранилище, UI) через Helm.
- **Масштабирование:** горизонтальный автоскейлинг для stateless, регулировка нагрузки через очереди для длинных задач.
- **Устойчивость:** blue/green деплой, канареечные выкладки моделей LLM, фолбэк на кэш при деградации моделей.
- **Runbook'и:** автоматические сценарии при сбоях адаптеров, ротации секретов, отказе провайдера моделей.

## 10. Наблюдаемость и обратная связь
- Структурированная телеметрия: трассировка шагов, спаны команд, метрики задержек инструментов.
- Аналитика чатов/сессий: процент успешных задач, MTTR, частота ручных вмешательств.
- Цикл обратной связи: inline-оценки, постинцидентный разбор с обновлением базы знаний.
- Детекция дрейфа: сравнение IaC и live-состояния, уведомления агента о расхождениях.

## 11. Тестирование и валидация
- Юнит-тесты адаптеров с моками SSH/K8s.
- Интеграционные сценарии на эфемерных кластерах (kind, k3d) и контейнеризированных сервисах.
- Учения по безопасности: симуляция высокорисковых команд для проверки механизма согласований.
- Режим shadow: агент наблюдает и рекомендует действия до получения права на исполнение.
- Постоянные red-teaming упражнения против prompt-injection и эскалации команд.

## 12. Детальный пошаговый план реализации
1. **Шаг 1. Подтвердить цели и ограничения (неделя 1)**
   - **Цель:** зафиксировать бизнес-цели, роли пользователей, ограничение по рискам и комплаенсу.
   - **Что сделать:** собрать требования от заинтересованных сторон, описать допустимые и запрещённые операции, определить ожидаемые SLA/MTTR.
   - **LLM-задачи:** «Сформируй документ Vision&Scope для DevOps агента с разделами: цели, пользователи, поддерживаемые сценарии, ограничения».
   - **Артефакт:** документ `docs/product/vision.md` + список рисков `docs/product/risk-register.md`.

2. **Шаг 2. Зафиксировать архитектуру и стек (неделя 1)**
   - **Цель:** выбрать языки, фреймворки, интеграционные паттерны.
   - **Что сделать:** подготовить ADR по выбору Python/TS/Go, описать целевую архитектуру (C4 level 1-3), согласовать используемые LLM-провайдеры (Gemini/Ollama) и схему расширения.
   - **LLM-задачи:** «Создай ADR для выбора FastAPI и LangChain»; «Сгенерируй диаграмму C4 level 2 в формате Mermaid».
   - **Артефакт:** каталог `docs/architecture/` с ADR (`adr-0001.md` и т.д.) и диаграммами.

3. **Шаг 3. Настроить репозиторий и окружение разработчика (недели 1–2)**
   - **Цель:** создать структуру проекта и обеспечить быстрый старт разработчиков.
   - **Что сделать:** инициализировать git-репозиторий, разложить каталоги согласно разделу 14, настроить Docker Compose для локального запуска сервисов, добавить `Makefile`/`taskfile.yml`, подготовить `.editorconfig` и `pre-commit`.
   - **LLM-задачи:** «Сгенерируй `docker-compose.dev.yml` с сервисами api, orchestrator, postgres, redis, pgvector»; «Напиши `Makefile` с целями install, lint, test, dev-up».
   - **Артефакт:** репозиторий с базовой структурой и документацией `README.md`.

4. **Шаг 4. Включить базовый CI/CD (неделя 2)**
   - **Цель:** автоматизировать проверки кода и сборку.
   - **Что сделать:** настроить GitHub Actions (или выбранный CI) с job'ами на линтинг (`ruff`, `black`, `eslint`), unit-тесты, сборку Docker-образов, загрузку артефактов; подготовить шаблоны релизов.
   - **LLM-задачи:** «Сконфигурируй workflow `.github/workflows/ci.yml` с матрицей Python/Node».
   - **Артефакт:** активный pipeline CI + документ `docs/ops/ci.md`.

5. **Шаг 5. Подготовить базовые сервисы данных (недели 2–3)**
   - **Цель:** обеспечить хранение состояния, кешей и артефактов.
   - **Что сделать:** описать Docker/Helm манифесты для PostgreSQL, Redis, MinIO, pgvector/Weaviate; подготовить миграции (Alembic/Liquibase), зафиксировать схемы таблиц.
   - **LLM-задачи:** «Сгенерируй SQL миграцию для таблиц sessions, audit_log, knowledge_base».
   - **Артефакт:** папка `infra/compose/data/` или Helm-чарты + документ `docs/ops/data-services.md`.

6. **Шаг 6. Описать реестр окружений и прокси (неделя 3)**
   - **Цель:** стандартизировать описание инфраструктурных профилей.
   - **Что сделать:** разработать JSON Schema для `environment-profile`, создать пример YAML, реализовать сервис `env-config` (FastAPI) с CRUD и валидацией, связать с Vault для секретов.
   - **LLM-задачи:** «Создай JSON Schema для environment-profile с секциями networking, auth, policies»; «Напиши FastAPI endpoint `/environments/{id}`».
   - **Артефакт:** каталог `apps/env-config/` + `docs/ops/environments.md`.

7. **Шаг 7. Настроить ingestion знаний (неделя 3)**
   - **Цель:** наполнить базу знаний runbook'ами и документацией.
   - **Что сделать:** определить источники (Git, Confluence, markdown), написать ETL (парсинг → очистка → эмбеддинги → загрузка в pgvector), добавить расписание обновлений.
   - **LLM-задачи:** «Сгенерируй Python-скрипт для парсинга markdown и записи эмбеддингов в pgvector».
   - **Артефакт:** пакет `data/ingestion/` + документ `docs/knowledge/ingestion.md`.

8. **Шаг 8. Реализовать маршрутизатор LLM и провайдеров (недели 3–4)**
   - **Цель:** обеспечить единый интерфейс к Gemini и Ollama.
   - **Что сделать:** создать модуль `llm-router` с абстракциями `LLMProvider`, реализовать адаптеры `GeminiProvider` и `OllamaProvider`, настроить авто-анонимизацию промптов, fallback, health-check.
   - **LLM-задачи:** «Сгенерируй класс `GeminiProvider` на Python, реализующий метод `complete(prompt, params)`»; «Напиши unit-тесты для fallback логики».
   - **Артефакт:** пакет `apps/orchestrator/llm_router/` + конфиг `config/llm.yml`.

9. **Шаг 9. Управление конфигурациями и секретами (неделя 4)**
   - **Цель:** централизовать настройки и безопасно хранить секреты.
   - **Что сделать:** интегрировать HashiCorp Vault или External Secrets Operator, описать политики ротации ключей LLM, реализовать загрузку конфигураций (Pydantic Settings) с поддержкой профилей окружений.
   - **LLM-задачи:** «Напиши модуль Python `settings.py`, читающий ENV/Vault и валидирующий структуры».
   - **Артефакт:** документ `docs/ops/secrets.md` + конфиги `config/`.

10. **Шаг 10. Реализовать сервис диалога и память (недели 4–5)**
    - **Цель:** поддерживать сессии и контекст пользователей.
    - **Что сделать:** создать FastAPI сервис `conversation`, реализовать CRUD диалогов, контекстные окна, retrieval augmented generation на основе pgvector, механизмы шифрования истории.
    - **LLM-задачи:** «Сгенерируй FastAPI router `/sessions` с методами create/list/append_message».
    - **Артефакт:** каталог `apps/api/conversation/` + ER-диаграмма `docs/architecture/db-conversation.png`.

11. **Шаг 11. Построить планировщик (Planner Agent) (недели 5–6)**
    - **Цель:** разбирать задачи на шаги с учётом профиля окружения.
    - **Что сделать:** реализовать графовое планирование (LangGraph/кастом), добавить управление подтверждениями, симулятор планов на моковых адаптерах, подключить данные из `env-config`.
    - **LLM-задачи:** «Напиши планировщик на LangGraph, который принимает `task`, `environment_profile` и выдаёт список шагов».
    - **Артефакт:** пакет `apps/orchestrator/planner/` + тесты `tests/unit/planner_test.py`.

12. **Шаг 12. Построить исполнитель (Executor Agent) и базовые инструменты (недели 6–7)**
    - **Цель:** выполнять команды в режиме read-only и проверять выводы.
    - **Что сделать:** реализовать адаптеры SSH, Kubernetes, Docker с dry-run и прокси-настройками, добавить потоковый вывод, логи, обработку ошибок.
    - **LLM-задачи:** «Создай класс `KubernetesExecutor`, который читает kubeconfig из профиля окружения и выполняет `kubectl get`».
    - **Артефакт:** каталог `apps/tool-executors/` + runbook `docs/runbooks/executor.md`.

13. **Шаг 13. Внедрить политиковый движок и guardrails (неделя 7)**

## 13. Провайдеры LLM и маршрутизация
- **Брокер вызовов:** модуль `llm-router` с plug-in интерфейсом (абстракции `LLMProvider`, `CompletionAdapter`), поддерживающий горячее подключение новых API и настройку политик выбора модели на уровне конфигурации.
- **Облачные модели:** Google Gemini 1.5 (Pro/Flash) — основной облачный провайдер; поддержка выбора региона, квот и ограничений по данным.
- **Локальные модели:** Ollama с Llama 3 70B/8B, Mixtral 8x22B (при необходимости — другие GGUF через llama.cpp). Локальный провайдер выступает fallback для приватных данных и офлайн-режима.
- **Расширяемость:** шаблонные адаптеры для будущих провайдеров (OpenAI, Anthropic, Azure, локальные GGML) с минимальным внедрением: реализовать интерфейс, описать маппинг параметров и зарегистрировать в конфиге.
- **Функции маршрутизации:** health-check провайдеров, кэширование ответов, логирование стоимости, автоматический фолбэк между Gemini↔Ollama, поддержка AB-тестов и динамического лимита токенов.
- **Безопасность и соответствие:** проксирование промптов через сервис санации (удаление секретов, PII), шифрование хранения, аудит вызовов, контроль экспорта данных для Gemini.
- **Наблюдаемость моделей:** сбор латентности, токенов, ошибок, отдельный дешборд SLA; регулярный пересмотр маршрутизации на основе метрик качества и бюджета.

## 15. Управление окружениями и контекстами
- **Реестр окружений:** централизованный каталог `environments/` с YAML-профилями (`env-id.yaml`) описывает прокси, jump-host, используемые пакеты, версии Kubernetes/Docker, допустимые namespace/кластер, переменные `HTTP(S)_PROXY`, ограничения по сети.
- **JSON Schema и валидация:** совместный пакет `env-schema/` для проверки корректности профилей на CI, поддержка обязательных полей (регион, тип доступа, политики согласования, секреты Vault).
- **Конфигурационный API:** сервис `env-config` публикует REST/gRPC/GraphQL API для агентов; контекст содержит идентификатор окружения, набор переменных окружения, mount secrets, правила прокси.
- **Контекст сессии:** при запросе пользователь выбирает профиль (`prod-k8s`, `dev-vm`, `lab-airgap`), планировщик подтягивает параметры (команды и шаблоны конфигураций, например `/etc/environment`) и включает их в промпт.
- **Прокси и сетевые требования:** каждый профиль несёт блок `networking.proxy` (адреса, списки обхода, сертификаты). Executor Agent применяет настройки перед запуском команд (export vars, проксирование пакетов, перенастройка пакетных менеджеров).
- **Каталог runbook'ов:** профили ссылками указывают на релевантные инструкции и чек-листы (например, «развёртывание nginx»), что упрощает автоматическое составление плана.
- **Локальные overrides:** поддержка пользовательских слоёв (`user-overrides/username.yaml`) для временных изменений прокси/доступов без правки базового профиля, с проверками и аудитом изменений.

### Пример профиля окружения
```yaml
id: prod-k8s
display_name: "Production Kubernetes"
type: k8s
cluster:
  name: prod-cluster
  context: prod-admin
networking:
  proxy:
    http: http://proxy.company.local:3128
    https: http://proxy.company.local:3128
    no_proxy: ".svc,.cluster.local,127.0.0.1"
  bastion: bastion.prod.company
auth:
  vault_role: prod/k8s/admin
  ssh_cert_role: prod-admin-cert
policies:
  risk_level: high
  require_approval: true
defaults:
  namespace: nginx-prod
  package_manager: apt
runbooks:
  - docs/runbooks/nginx/deploy.md
notes: "Использовать прокси и bastion; доступ только через утверждённые change-tickets"
```
